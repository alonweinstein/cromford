# Egress allowlist per build stage (BH-4492)

**What it is:** `run_attempt` in `bin/agent-call.sh` runs a build-stage CLI
inside its own network namespace when the stage has an
`egress.stage.<stage>.hosts` settings row. `bin/lib/egress.sh` decides and
`bin/egress-proxy.py` is the only way out: listed hosts pass, everything else
gets 403 and a `DENY` line. Seeds: execute = model APIs + npm/PyPI, review =
model APIs only. Details: [the note](../notes/2026-10-05-BH-4492-egress-allowlist.md).

**How to drive it:**

| what | how |
|---|---|
| the suite (proxy, lib, real agent-call with a fake `claude`, real evidence-summary) | `HARNESS_TEST_SANDBOX=1 bash tests/egress-allowlist-test.sh` |
| on the test host | `bin/remote-gate.sh . tests/egress-allowlist-test.sh` |
| one host against a list | `python3 bin/egress-proxy.py match --hosts "<list>" host:port; echo $?` |
| a finished build | `cat $BUILD/egress-state.txt; grep DENY $BUILD/egress.log` and the PR's `egress allowlist` row |

**What must never regress:**

- A stage with no row, a call outside `builds/`, and the value `off` run with
  the exact argv they had before.
- An unreadable row falls back to the model hosts only, never to "allow all"
  and never to "allow nothing".
- A box that cannot fence alerts once per stage per day and never refuses the call.
- Every request line on a kept-alive HTTP connection is checked.
