Self-Serve Migration Endpoint

Each OS app applies its own merged, deployed, code-reviewed SQL through an internal-token-gated endpoint — the watcher fleet triggers application without ever holding a database credential. Replaces the "paste owner DB URLs onto bot boxes" idea, which is rejected permanently.

SQL never travels — only a filename DB creds stay inside each app's Vercel env Human still merges every migration PR (tier-2) ~2 AI sessions to ship

01 The problem

Every merged PR that carries scripts/migrations/*.sql currently waits for a human to apply the SQL to prod (Supabase Management API for project-2/project-1, turso db shell for project-3/project-4). The hub's check-migration-prs.sh pings Telegram until someone does. At fleet build velocity this backlog hit 10 PRs in two days, and the orchestrator's proposed fix — provision owner DB credentials onto the watcher boxes — was refused: a compromised always-on box running --dangerously-skip-permissions sessions would hold full owner access to client production databases. The blast radius today is a repo-scoped PAT; that proposal made it a client's entire book.

The lesson that shaped the current rule: "a merged PR containing migrations needs its SQL applied to prod BY A HUMAN — 3 outages in one night" (MULTI-MACHINE-PLAN, Known Sharp Edges). This spec automates the application step only, keeping the human at the merge gate and removing raw SQL and raw credentials from every automated surface.

02 Security model — the four properties

No SQL in transit
The endpoint accepts a filename, never SQL text. The SQL executed is the file baked into the app's deployed bundle — meaning it was PR-reviewed, adversarially reviewed (Fable), human-merged (migrations force tier-2), and deployed by Vercel before it is even addressable. A compromised watcher can only ask an app to run SQL that already shipped through the full gate chain.
No creds outside the app
The app executes with the DB connection it already holds in its own Vercel env. Nothing new is provisioned anywhere. Watcher boxes keep exactly what they have today: a repo-scoped PAT + app-level internal tokens.
Human merge gate intact
run-build.sh already classifies any diff touching migrations/|\.sql$|schema\.prisma as tier-2 → PR waits for the operator. This spec does not change that. What was manual-after-merge becomes automatic-after-deploy.
Additive-only, enforced
A statement classifier refuses destructive SQL (§05) even though the file passed review — defense in depth for the standing additive-only schema law. Destructive migrations remain human-applied by design.

The deploy step is load-bearing: a file is only "pending" once it exists in the running deployment's bundle, which by construction means the merge commit is live. The watcher can never apply ahead of the code that expects the schema.

04 API contract (per app)

RouteAuthBehavior
GET /api/internal/migrations/statusBearer MIGRATION_TOKENLists bundle files vs ledger: {applied:[…], pending:[{filename, checksum, statements}]}. Deterministic — this is how the watcher knows anything is waiting.
POST /api/internal/migrations/applyBearer MIGRATION_TOKENBody {"filename":"2026-07-24-x.sql"}. Validates → classifies → executes per-statement → ledger row → {ok, applied, perStatement:[…]}.

Request validation, in order

  • Token: timing-safe compare, .trim() both sides (the CRON_SECRET lesson). 404 on failure, never 401 — the route stays invisible.
  • Filename: basename() only, must match ^\d{4}-\d{2}-\d{2}-[a-z0-9-]+\.sql$, must exist in the bundled scripts/migrations/ dir. No traversal surface.
  • Ledger check: already applied with same checksum → {ok:true, alreadyApplied:true} (idempotent no-op). Applied with different checksum → refuse + alert (a merged file was edited after application — a human must look).
  • Classifier (§05) on every statement. One refused statement refuses the whole file.

MIGRATION_TOKEN is a new, separate secret (not INTERNAL_API_TOKEN): least privilege, independently rotatable, and revoking migration ability never breaks board reads. Lives in each app's Vercel env + the matching box's <project>.env. Every call also logs to the just-shipped InternalApiCall audit table.

Vercel gotcha (known, planned for): serverless functions don't include arbitrary repo files — each app's next.config needs outputFileTracingIncludes for scripts/migrations/** so the SQL is readable at runtime. Miss this and /status honestly reports an empty dir (fail-safe: nothing to apply, nothing breaks).

05 The applied-ledger

CREATE TABLE IF NOT EXISTS "MigrationApplied" (
  "id"           TEXT NOT NULL,            -- cuid
  "filename"     TEXT NOT NULL,            -- unique: exactly-once per file
  "checksum"     TEXT NOT NULL,            -- sha256 of file body at apply time
  "statements"   INTEGER NOT NULL,         -- how many were executed
  "status"       TEXT NOT NULL,            -- applied | failed | refused
  "perStatement" JSONB,                    -- [{i, firstLine, ok, error?}]
  "actor"        TEXT NOT NULL,            -- 'watcher' | 'human:<name>'
  "appliedAt"    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT "MigrationApplied_pkey" PRIMARY KEY ("id")
);
CREATE UNIQUE INDEX IF NOT EXISTS "MigrationApplied_filename_key" ON "MigrationApplied"("filename");
-- Postgres apps: + ENABLE ROW LEVEL SECURITY + REVOKE anon/authenticated (standing rule)

Bootstrapping is self-hosting: the ledger table's own migration is the first file each endpoint applies (the route creates it inline with IF NOT EXISTS on first call). Historical migrations already applied by hand get backfilled as actor:'human:backfill' rows so /status starts honest, not with 40 false pendings.

06 Statement classifier

ClassVerdictStatements
Additive DDLALLOWCREATE TABLE/INDEX IF NOT EXISTS · ALTER TABLE … ADD COLUMN · ALTER TYPE … ADD VALUE · CREATE POLICY
Security postureALLOWENABLE ROW LEVEL SECURITY · REVOKE (RLS is required on every CREATE TABLE in Postgres apps — post-apply check warns if missing)
Idempotent seedsALLOWINSERT … ON CONFLICT DO NOTHING · SQLite INSERT OR IGNORE
Bounded backfillsALLOW+FLAGUPDATE with a WHERE clause — executed, but surfaced loudly in the report beat for human eyes
DestructiveREFUSEDROP TABLE/COLUMN/TYPE · TRUNCATE · DELETE · UPDATE without WHERE · GRANT to anon/authenticated · anything unparseable

A refused file isn't a dead end: the ledger records status:'refused', the beat tells Telegram exactly which statement tripped, and that migration is applied by a human through today's channels. Destructive schema change should hurt a little.

08 Harness wiring

  • New bin/apply-migrations.sh <project>: GET /status → for each pending file, POST /apply → beat per result (kind:"migration", applied/refused/failed + per-statement detail) → on success, drop a line in the project log. Runs on each box via cron (:*/15) — and the triage prompt's results-sweep mentions applied migrations in its board close-out comments, so clients see "schema shipped" in plain language.
  • Changed check-migration-prs.sh (hub): stops pinging Telegram for a merged migration PR once the app's /status shows its file applied — the ping now means "needs a HUMAN" (refused/failed/pre-endpoint repos only). The nag becomes signal, not noise.
  • Unchanged: tier-2 classification, the human merge, dev-branch application during builds (worktrees still use apply-sql.mjs against the dev DB).

09 Failure modes

ScenarioBehavior
Statement 3 of 7 fails mid-fileLedger row status:'failed' with per-statement results; alert beat. Files are idempotent by repo convention, so after a human fixes the cause, re-POST completes the remainder — IF NOT EXISTS skips what landed.
Same file POSTed twice (double cron)Unique ledger index + checksum check → second call returns alreadyApplied:true. Exactly-once.
File edited after being appliedChecksum mismatch → refuse + alert. Convention: never edit an applied migration; write a new file.
Endpoint down / not yet shipped in a repo/status unreachable → watcher does nothing, hub keeps pinging Telegram exactly as today. Failure mode = the status quo.
MIGRATION_TOKEN leaks from a boxAttacker can trigger application of already-merged, already-deployed, classifier-filtered, additive-only SQL — the thing the system does anyway. Rotate one Vercel env var. No data read or write surface.
